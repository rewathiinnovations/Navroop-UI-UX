# Agent guide — Navroop / Open Lovable

Navroop is an invite-only admin shell around Open Lovable (Next.js App Router, React 19, Tailwind, Prisma/Postgres, E2B, Firecrawl). Brand the product as Navroop. Default theme is light. Do not revert studio/admin chrome. Generation runs in the background via `GenerationProvider`.

## Product map

Authenticated app chrome: `components/layout/Sidebar` + studio shell. Generation is backgrounded via `GenerationProvider`. One Next.js server on `:3000` — only the dedicated **dev server** agent may start/restart it, run `prisma generate`, or replace locked Next/Prisma binaries (`single-dev-server.mdc`). Coolify production is `docker-compose.yml` (`app` + `postgres`); local Postgres on host `5433` is `docker-compose.dev.yml`. See `docs/coolify.md`. `NEXT_PUBLIC_APP_URL` is set explicitly in `docker-compose.yml` and `assertInternalOrigin()` (`lib/api/internal-origin.ts`) refuses to boot in production when it is unset, unparseable, or a different host from `APP_URL` — it still only warns elsewhere. It no longer guards self-fetches (there are none); it guards the GitHub App Manifest callback and the static-preview origins.

- **API auth gate** — `proxy.ts` denies every request under `/api` and `/preview-static` unless it matches `lib/auth/public-routes.ts` (`PUBLIC_API_ROUTES`). New routes are private by default. The gate is coarse: it decodes the Auth.js JWT for signature and expiry only, never touching Prisma. Membership, project ownership, ADMIN role, and the deactivated-user check (`getSessionUser` re-reads `isActive`; the `auth.ts` `jwt` callback strips a revoked token) stay in the routes — defence in depth, do not remove them. Denials are JSON 401 `{ error: { message, code, requestId } }`, never a redirect. Allowlist entries need an explicit path, explicit methods, a `reason`, and an `ownMechanism`; the Auth.js catch-all is listed action by action so `/api/auth/me` stays private. Guards: `tests/unit/api-route-auth.test.ts` (walks `app/api/**`, pins the public set, pushes every endpoint through the real proxy), `scripts/check-public-routes.ts` (verify step, rejects wildcards and prints the allowlist size), and the unauthenticated probe in `scripts/smoke-test.ts` (`SMOKE_AUTH_PROBE=off` to skip).
- **No self-fetch between routes** — an API route never calls a sibling route over HTTP on its own origin. The work lives in `lib/` and both the route and the internal caller call it directly: `lib/generation/analyze-edit-intent.ts`, `lib/sandbox/read-files.ts`, `lib/sandbox/install-packages.ts` (`precheckInstall` returns JSON errors before the SSE stream opens), `lib/sandbox/restart-dev.ts`, `lib/sandbox/detect-packages.ts` (`activeSandboxProvider` + string `runCommand`; the live follow-up is still `apply-ai-code-stream` → `installPackages`). Routes stay as thin wrappers (authenticate, parse, call, map). The `internalCallHeaders` cookie relay is gone — do not reintroduce it. Failures are typed results, never a silent `if (response.ok)` else branch; inside a Job, record them with `recordJobStepFailure` (`lib/jobs/step-failure.ts`) so they reach the recovery panel and `/admin/jobs`. Typed misses and unexpected throws from `analyzeEditIntent` / `readSandboxFiles` call `recordJobStepFailure` (`analyze-edit-intent` / `read-sandbox-files`).
- **Instance self-identity** — `lib/runtime/self.ts` `getSelfIdentity()` → `{ coolifyAppUuid, gitSha, instanceId, environment }`, cached per process. The only reader of `process.env.COOLIFY_APP_UUID`; Sentry restart, `/api/admin/health/rollback`, and `scripts/rollback.ts` all go through it and share `SELF_UUID_NOT_CONFIGURED`. Surfaced on `/admin/health`. Blank is the same as unset. App identity, not an integration credential — it does not belong in the Integration store.
- **Projects API** — `/api/projects`, Prisma `Project` (`lib/projects`)
- **Plan/Build** — `ProjectPhase` + `/api/projects/[id]/plan`; workspace chat modes `plan` | `build`. The plan is the first-build gate: the created project's arm (`sessionStorage` `navroop_arm_<projectId>`, written by `armProjectGeneration`, taken once by the workspace for that id only — never a global `navroopPrompt` / `targetUrl` / `autoStart`, which auto-started a paid build on the next project opened in the tab) is shown in chat during PLANNING and does not start generation; Approve (or skip-planning / URL import) starts the only first build. A URL import is not armed at all — it resumes from its own `ImportSource` row. A job that dies before any plan or site exists resumes to PLANNING (`resumablePhaseFromEvidence`); COMPLETE means a finished site (`lastCode` / checkpoint — not job `filesWritten`, which is stream progress). Stream complete is not enough to `succeedJob` / COMPLETE. A streamed BUILD with no `lastCode` / checkpoint and sandbox FAILED or DEAD fails as `sandbox_unavailable` via `settleStreamedGeneration` (`lib/jobs/settle-generation.ts`). Chat says the generated files were not saved because the workspace never became ready (or the existing boot error if create already failed the job). Recovery Try again starts a new billed build; the last files were not saved. `requestFollowUpPlan` still rolls a live site back to COMPLETE when the follow-up is discarded.

New projects default **NEXTJS**. PromptHero + pending-prompt (`navroop_pending_prompt`, the two heroes only — the template sheet keys its own `navroop_template_draft_<id>`) persist `{ text, stack, savedAt, designDirection, importMode, templateId }` (defaults NEXTJS + `minimal` + `reimagine`). A signed-out hero submit is handed to `AuthModal` in memory (`createSignedOutSubmit`) and spent once; leftover draft text never creates a project on a later sign-in.

- **Static preview** — Prisma `PreviewBuild` + `Project.previewMode` / `activePreviewBuildId`. `lib/preview/` builds a static snapshot inside the generation sandbox, uploads it, then calls `killSandbox`. Viewing does not keep a VM alive. Serve from `/preview-static/{projectId}/…` (or `preview-static.{zone}`) with a 2-hour signed URL token — not a cookie. Workspace **Live mode** is the escape hatch (credits). Failed Next.js export sets `LIVE_SANDBOX` without mutating the user’s `next.config`. `withTemporaryNextExport` forces `output: 'export'` for the build and restores the original bytes, and **it must match the config's module system**: the NEXTJS scaffold writes `next.config.mjs`, so appending `module.exports` (the CommonJS path) threw `ReferenceError: module is not defined in ES module scope` and every static preview fell back to LIVE_SANDBOX. ESM configs are handled by parking the original in a `.navroop-original` sidecar of the same extension and writing a wrapper that imports and spreads it; the sidecar is removed in the `finally` so it never reaches a checkpoint. Guard: `tests/unit/next-export-esm-config.test.ts`. Retention: active + 2 recent + bookmarked (daily thin-checkpoints). Preview mode and Coolify deploy mode are independent. One generation produces one preview capture (`capturePreviewAfterGeneration` keyed by project + checkpoint); a newer checkpoint still captures. `activePreviewBuildId` is adopted only if the incoming build is newer (`createdAt`), so a stale overlapping capture cannot overwrite. After apply, `persistProjectGeneration` may return `previewNotice`; `generation-runtime` surfaces it in chat (`surfacePreviewNotice`) so a failed preview is not described as a failed build, and the same sentence is not added twice if `saveCurrentProject` also persists.

- **Checkpoints** — `/api/projects/[id]/checkpoints`, Prisma `Checkpoint`. Latest checkpoint is the source of truth for disposable sandboxes. `readSnapshot` (`lib/checkpoints/snapshot-store.ts`) throws `SnapshotReadError` when storage or gunzip fails — an empty array means the checkpoint is genuinely empty, never "could not read". Callers (`loadRestoreFiles`, `collectPublishFiles`, ZIP export) must not catch that and fall through to `project.lastCode`.
- **Sandbox providers** — Prisma `SandboxProviderConfig` + `lib/sandbox/router.ts` `selectProvider`. Drivers **e2b | modal | daytona** only (credentials via constructor, not env). Default strategy `free_first` (monthly free credit, then smallest one-time). `unknown` stays eligible so a first boot can run; known-healthy outranks unknown, unknown outranks degraded (never exclude unknown). The pick carries `selectionReason`; ADMIN shows it as **Next pick**; Job `sandboxAttempts` records who was tried plus that reason (`ok` means the boot reached READY — not that the provider was selected or that `create()` returned a handle; a later ready/install miss flips the last row via `markSandboxAttemptBootFailed`), and `sandboxSkipped` lists only eligible rows that beat the pick on cost/credit/priority but lost on health (not every considered row). Same English as Next pick; no secrets in `resourceIds`. Sticky: probe/kill use the stored `Project.sandboxProviderConfigId`. Failover records attempts on the Job. **`createWithFailover` wraps the whole boot, not just `createSandbox`** — restore, install, the preview URL and `pollPreviewReady` all run inside the callback, and a provider that fails any of them is torn down (`source: 'boot'`) before the next candidate is tried. Creating a VM is the step that almost never fails; the real failure is a vendor returning a handle and then never serving the dev server, and while that threw past the loop one flaky provider failed every build on the instance with an active second vendor untouched. The callback wraps a non-`SandboxBootError` throw in one, naming the step it died on — the providers do not all use that type (`assertInstallSucceeded` throws a plain `Error`), and without the wrap a Modal `npm install` failure ended the boot in ten seconds with an eligible E2B row untouched. `isSandboxBootFailover` (not the transport-only `isFailoverError`) is the classifier: restore/install/dev/ready steps move on, `SANDBOX_LIMIT` / `SANDBOX_MINUTES` / `NO_CHECKPOINT` do not, because those repeat identically on every provider. The `previewMode = STATIC` write stays outside the loop so it names the winner. Guard: `tests/unit/sandbox-boot-failover-scope.test.ts`. Circuit: 3 fails → down 10 min. Cron `POST /api/cron/check-sandbox-providers` every 5 min. ADMIN `/admin/sandbox-providers`. Client chrome must not import `lib/sandbox/test-run`, `lib/sandbox/teardown`, or `lib/security/url-guard` — those pull `node:async_hooks` / `node:dns` into the Turbopack browser graph and 500 the page on first compile; use `lib/sandbox/provider-check-copy` and `lib/security/url-guard-messages`. Test and the probe persist `healthStatus` after create + `echo` + shutdown + a returned preview URL (not fetched) — they do not start a preview or run a build; `healthy` means that scope. `applyPreviewUrlCheck` also rejects empty, unparseable, non-http(s), and `undefined`/`null` hostnames (`https://undefined`) without fetching. Probe failures write the same driver-named English as Test. An all-skipped probe records a skip (`CronRun` failed), not a silent pass. `toPublicProvider.monthsRemaining` is `null` when there is no 30-day burn (never `Infinity`). First boot migrates `E2B_API_KEY` to "E2B (migrated)" then ignores the env var. `POST /api/admin/sandbox-providers` refuses a blank credential per driver (E2B/Daytona apiKey, Modal tokenId+tokenSecret) — a keyless row used to save fine and then fail every boot with the provider's own "authorization header is missing" 401, which reads like a code bug. `@daytona/sdk` and `form-data` are `serverExternalPackages` in next.config.ts: bundled, the SDK's dynamic `require('form-data')` dies at the first file upload. Provider dashboards are authoritative. `modal` is pinned `0.9.0` and boots `node:20` (not Python) so `setupViteApp` can run `npm` / Vite / Next; create requests `encryptedPorts: [5173]` (`appConfig.e2b.vitePort`); a missing `node`/`npm` asks `terminateLive` (`modalMissingDevBinariesMessage` says "asked to stop"). E2B `runCommand` sends a Python cell that prints `STDOUT:` / `STDERR:` / `Return code: N`; that envelope is a wire format between the cell and `commandResultFromE2BExecution`, which **unwraps it** (`unwrapE2BPrintedStreams`) before any caller sees `stdout`. Do not return it raw: the static preview lists files by splitting `find` output line by line (`sandboxFromProvider.listFiles`), so the three marker lines became filenames and the capture tried to write `previews/<project>/<build>/STDOUT:` — illegal on Windows, ENOENT, and a generation that had succeeded ended with a null `previewUrl`. The return code is still parsed from the raw text. Guard: `tests/unit/e2b-command-envelope.test.ts`. Modal writes use `filesystem.writeText` with `absoluteSandboxPath` — not `printf`+`JSON.stringify`. Daytona's unused-shell fallback is base64 (`base64DecodeWriteCommand`). E2B `files.write` already takes a Buffer. Test and the probe do not `npm install`, start Vite, or fetch the preview URL. `@daytona/sdk` is pinned `0.205.0` (both 0.x — exact versions; minors may break).
- **Sandbox lifecycle** — `lib/sandbox/manager.ts` `ensureSandbox(projectId)` routes through `selectProvider` then the chosen driver. Prisma `SandboxStatus` (`NONE|BOOTING|READY|DEAD|FAILED`) on `Project` with `sandboxStartedAt` / `sandboxLastUsedAt`. Keep `sandboxId` + `previewUrl`. POST/GET `/api/projects/[id]/sandbox`. Idle reap: `POST /api/cron/reap-sandboxes` (Bearer `CRON_SECRET`, `SANDBOX_IDLE_MINUTES` default 5; 5 min early shutdown when there is no HTTP activity and no active job). Expected ≥80% fewer sandbox minutes because viewing uses static preview. Minutes accrue on kill and during the reaper pass for READY, BOOTING, and FAILED rows that still have a `sandboxId` (`bumpStart` so a leak keeps billing; `Workspace.sandboxMinutesUsed`, `Plan.monthlySandboxMinutes` default 300) and on the provider config (`minutesUsed` / `spendUsd` / `creditRemainingUsd`). Cold start refused when the monthly total is exhausted. No E2B `Sandbox.create` outside `lib/sandbox/`. `setupViteApp` / `installAndStartDev` hard-fail a non-zero `npm install` and call `teardownProvider` (Modal/Daytona via `assertInstallSucceeded`; E2B via `assertE2BInstallSucceeded`). `pollPreviewReady` gates READY on a successful GET (`response.ok` or 304) — a truthy URL is not enough; timeout is `FAILED` with a named English message. Three clocks, not one: `BOOT_WAIT_MS` (90s waiter deadline), `BOOT_CLAIM_FRESH_MS` (10 min claim freshness), `READY_POLL_MS` (90s HTTP-ready window). `FAILED` is retryable: `waitForInflightOrReady` returns null so `claimBoot` can CAS FAILED→BOOTING; the last error stays in `lastErrors` until the next attempt finishes. `killSandbox` sets NONE and clears `sandboxId` only when teardown is not a leak; a leak keeps the id and `sandboxStartedAt` so later passes still bill. The reaper retries a leak once per pass unless the provider circuit is open, counts a reap only when the kill really stopped, and also walks FAILED rows that still carry a `sandboxId`. Permanent denials (minutes, sandbox cap, no provider) fail fast without a VM — the provider circuit (3 fails → down 10 min) plus failover already cover a dead provider. `claimBoot` treats BOOTING as live for `BOOT_CLAIM_FRESH_MS`, not the 90s waiter/ready-poll window; stealing a stale claim accrues minutes first and leaves `sandboxId` for probe/reuse. A lost `claimBoot` throws ("The workspace is still starting. Try again.") instead of creating a second billable VM. `waitForInflightOrReady` never adopts its own promise — that deadlocked the boot on itself. `createSandboxOrTerminate` (and each driver's create catch) calls `teardownProvider` (never throws) when `create()` throws. `TeardownResult` is `stopped` | `already_gone` | `could_not_stop`. A leak is recorded on AppSetting `sandbox.teardownLeaks` (same counter pattern as `ssrf.privateRejects`, shown on `/admin/usage`) and `sandboxId` stays on a FAILED boot so the reaper can find it. Copy (`unusedSandboxTeardownSuffix`): "asked to stop" when we tried and do not know, "stopped so it is not billed" only on proven `stopped`/`already_gone`, "could not be shut down and may still be billed" on `could_not_stop`. Mid-generation `restartDevServer` (`lib/sandbox/restart-dev.ts`) uses the same poll; a failed restart is a typed degraded result (generated code kept, VM stays up), not a failed build. E2B `runCommand` / `installPackages` parse the printed subprocess `Return code` (`lib/sandbox/e2b-command-result.ts`); `Execution.error` is a Python exception, not the command exit. Daytona `runCommandLive` uses `commandResultFromDaytonaExecute` (`lib/sandbox/daytona-command-result.ts`): `@daytona/sdk` 0.205.0 types `ExecuteResponse.exitCode` as a required `number`, but a missing runtime value is exit 1, not 0. `apply-ai-code-stream` closes with `applyOutcome` (`lib/jobs/copy.ts`) — a clean write is still "Successfully applied N files"; file-write / Morph misses send the same warning frame ("N files were applied. M files could not be written — try again") and record `write-file:…` via `recordJobStepFailure`. Preview / package errors already have their own frames and do not change that sentence. GenerationWorkspace (`components/workspace/GenerationWorkspace.tsx`, imported by `/project/[id]`) shows that same sentence via `applyPageCopy` (`lib/generation/apply-page-copy.ts`); do not hard-code "Applied N files successfully!". `/generation` is not a route. The unused JSON `apply-ai-code` route also calls `applyOutcome` so its `message` cannot drift. E2B `createSandbox` refuses a missing `getHost` (never `https://undefined`), asks teardown, and uses `sandboxMissingPreviewUrlMessage` — it does not require HTTP 200 at create time. E2B `listFiles` throws `sandboxListUnreadableMessage` when stdout is not a JSON array of paths (never `[]`). All three drivers share one reconnect contract: `false` only on evidence the VM is gone, throw when we could not tell (`sandboxReconnectUncertainMessage`), `true` only with a real preview URL. Modal reattaches via `sandboxes.fromId` plus `tunnels()`. `probeExisting` treats an uncertain `reconnect()` as not-gone: it throws, writes no DEAD, boots no second VM, and restores a post-claim row to READY; a missing or undefined preview URL is uncertain. Reconnect copy (`sandboxReconnectMissingPreviewUrlMessage`) says the sandbox "is still running and may still be billed" — it never claims the VM was stopped. New snapshots are gzip objects at `snapshots/{projectId}/{checkpointId}.json.gz` (`writeSnapshot` / `readSnapshot`). `fileSnapshot` Json is legacy-read only. Bookmark + thin cron (`CHECKPOINT_RETENTION_DAYS`, default 7). Workspace storage ledger: single-row Prisma `Workspace` (`id=default`, `storageBytes` / `storageLimitBytes`).
- **Assets** — Prisma `ProjectAsset` + `lib/assets` + `lib/storage`; workspace Assets tab; `/api/projects/[id]/assets`. `STORAGE_DRIVER=local|s3` (ElasticLake: `ELK_*`, `forcePathStyle: true`), Unsplash stock, `NEED_IMAGE:` intercept. `s3Get` / `s3Exists` / `localExists` rethrow anything that is not not-found (`isObjectNotFoundError`; local also treats `ENOENT`/`ENOTDIR` as absent) — a permission or network miss is not "missing".

Modes `reimagine` (default) | `replicate`. Progress in chat. `POST /api/projects/[id]/import`. Workspace top bar shows the source URL. Private-range rejects increment `AppSetting` `ssrf.privateRejects` and show on `/admin/usage`. IMPORT Try again goes through `streamProjectImport`, not a generated build. `/admin/jobs` failed rows show `errorMessage` via `jobAdminFailureLine`. IMPORT Try again goes through `streamProjectImport`, not a generated build.

## Do not

- Dump `omni-*` / `gstack-*` / Coolify / WHM skill trees into this repo (still available from `~/.cursor/skills/`)
- Touch Next.js version or unrelated runtime unless asked

- Interpolate a composed `Prisma.sql` / `Prisma.join` / `Prisma.raw` fragment into a `` prisma.$queryRaw`…` `` / `` $executeRaw`…` `` tagged template. It works under plain Node (so Vitest passes) but binds the fragment as a parameter inside the bundled Next server, producing `SET $1` and Postgres 42601 — that is what silently killed every job heartbeat. Build the SQL text and number the placeholders yourself, then use `$queryRawUnsafe` / `$executeRawUnsafe` (column names from source literals only, values always bound). Guard: `tests/unit/raw-sql-composition.test.ts`.
- Let a `'use client'` file reach a Node-only builtin or a server-only module (Prisma, `lib/db`, `lib/logger`, `lib/sandbox/test-run`, `lib/security/url-guard`, an admin `load-admin`). Turbopack then puts `node:async_hooks` / `node:dns` in the browser graph and the route 500s on a cold compile — `next dev` stays up, so the page looks fine until someone loads it cold. Keep user-facing copy in a client-safe sibling (`lib/sandbox/provider-check-copy.ts`, `lib/security/url-guard-messages.ts`, `lib/import/error-messages.ts`) and give client components their own serialisable prop types instead of importing the loader for its types. Guard: `tests/unit/client-import-boundary.test.ts` walks value imports from every client file, stops at `'use server'`, and still fails a type-only import of a denylisted server module. Neither `tsc` nor Vitest sees this class otherwise — only `next build` or a cold dev compile.
- Create throwaway `.ts` / `.tsx` files at the repo root. `tsconfig` `include` is `**/*.ts`, so a scratch file there fails `tsc --noEmit` with TS6053 (or worse, typechecks as app code).
- Run a second `vitest --coverage` in this checkout while another is in flight. Both write `coverage/.tmp` and the later run (or the coverage table) is garbage.
